# 附錄 A. 公司 PC 系統詳細清單

> 本附錄把筆者所在的 MMORPG 開發商 A 的公司 PC 環境,從硬體到工具、知識資產、驗證材料,彙總在一張清單裡。為了讓讀者一眼看清正文中多處提到的"用這樣的工具""用這樣的 atom 結構""用這樣的報告"在現實中究竟以怎樣的規模與組合存在,筆者做了這份整理。文中的實名與專有名詞均已匿名化;數值會隨時點而變化,因此請不要將其當作絕對值,而應作為比例與構成來閱讀。

閱讀本附錄有兩種方法。一種是逐項對照自己的環境。把"我用什麼引擎、用什麼協作工具、知識資產以什麼形式積累"填進同樣的格子裡,自己的空白欄就會顯現出來。另一種是看整體構成的平衡。工具多並不等於環境好,重要的是引擎、策劃、美術、協作、AI 這五條軸是否彼此不掣肘、相互咬合。比起單個專案本身,更請留意它們交織而成的整體結構。

---

## A.1 系統概覽

首先是作為基礎的硬體與作業系統。一旦真正開始大量使用 AI 工具,就會遇到在本地執行擴散模型(diffusion)或 STT(語音識別)的場景,因此記憶體與 GPU 的餘量會直接變成工作速度。下面的配置請當作接近下限的基準線來看——"到這個程度就能順暢運轉"。

### A.1.1 硬體

| 專案 | 規格 |
|---|---|
| CPU | 桌面工作站級 |
| RAM | 64GB 以上 |
| GPU | UE5 開發用(相容 CUDA) |
| 儲存 | SSD 2TB + NAS 共享 |
| 顯示器 | 27 英寸 2 臺 |

RAM 與 GPU 這兩行是核心,因為經常會遇到同時開著引擎編輯器、本地 LLM 輔助工具和影像生成的時刻。

### A.1.2 作業系統與基礎環境

| 專案 | 值 |
|---|---|
| OS | Windows 11 Pro |
| 虛擬化 | WSL2(Ubuntu),按需 |
| 備份 | 每日自動 |

WSL2 不是一直開著,而只在需要執行 Linux 專用工具時才呼叫。備份以每日自動方式執行——這是本表中最重要的一行。

## A.2 工具清單

工具分為五類:引擎與工具、設計與策劃、美術、協作與運營,以及 AI 與 LLM。並非一個人會用到全部五類,但作為策劃,每天都會在設計與策劃、協作與運營、AI 與 LLM 這三類之間往返。請注意,每一類都呈現"一兩個必備 + 輔助"的形態。

### A.2.1 遊戲引擎與工具

| 工具 | 用途 |
|---|---|
| Unreal Engine 5.7 以上 | 主引擎 |
| Visual Studio | 程式碼 |
| Rider | C# IDE(輔助) |
| Perforce 或 SVN | 程式碼與資產版本管理 |

引擎與版本管理是一對。策劃也必須會用版本管理客戶端,因為資料表與設計文件都在同一個倉庫裡運轉。

### A.2.2 設計與策劃

| 工具 | 用途 |
|---|---|
| Excel | 資料表 + VBA 宏 |
| Markdown 編輯器 | 設計文件與會議記錄 |
| Figma | UI 與線框圖 |
| Mermaid | 圖表 |

這是策劃的日常工作臺。Excel 是資料的大本營,Markdown 是文字的大本營,也是 AI 工具嵌入最深的兩個點。Mermaid 之所以單佔一格,正如正文所強調的,是因為圖示就是達成共識的語言。

### A.2.3 美術

| 工具 | 用途 |
|---|---|
| Maya / Blender | 3D |
| Substance 3D | 紋理與材質 |
| Photoshop | 2D 與插畫 |
| Stable Diffusion(SDXL) / ComfyUI | 自託管的概念圖與紋理正式量產(LoRA·ControlNet) |
| Midjourney | 初期情緒板(輔助) |

雖然不是策劃直接使用的工具,但在與美術組來回溝通概念時,瞭解對方手上有哪些工具,會讓需求的清晰度大不相同。正式量產以自託管的 Stable Diffusion(SDXL)/ComfyUI 為主軸——因為不把素材上傳到外部即可保護 IP,並且能用角色 LoRA·ControlNet 在每次反覆生成時都控制同一人物的一致性。像 Midjourney 這類封閉式工具,只在最初摸索專案基調的早期情緒板階段作為輔助使用,而在需要一致性與反覆控制的正式量產中不使用。

### A.2.4 協作與運營

| 工具 | 用途 |
|---|---|
| 協作工具(ClickUp) | 任務 |
| 內部即時通訊工具 | 即時溝通 |
| 自建 Wiki | Wiki 與長期文件 |
| 自建門戶網頁 | 統一介面(20.3) |

溝通的時間軸決定了工具的劃分。需要即時性的即時溝通走內部即時通訊工具,待辦事項走協作工具(我們團隊用 ClickUp),需要長期留存的知識走自建的 Wiki——即使把任務追蹤器換成 JIRA·Redmine、Wiki 換成 Confluence·Notion,無論即時通訊工具是哪一個,本書的思路都不變。自建門戶網頁是把這三者與 AI 工具在同一螢幕上連線起來的統一入口,將在 20.3 中詳細展開。

### A.2.5 AI 與 LLM

| 工具 | 用途 |
|---|---|
| Claude(Opus + Sonnet) | 主 LLM |
| GPT-4 | 備選 |
| Whisper(自託管) | 語音識別(STT) |
| Stable Diffusion | 影像生成(自託管) |
| MCP 伺服器 | 工具整合(20.4) |

主力用 Claude,GPT-4 作為交叉驗證與備選。敏感的語音與影像不外發、而以自託管方式處理——這一原則體現在 Whisper 和 Stable Diffusion 這兩行裡。MCP 伺服器是把這些工具嵌入工作流的黏合劑,其結構將在 20.4 中說明。

## A.3 atom 清單

atom 是把正文講過的"決策的最小單元"落到檔案裡的知識碎片。下表展示這些 atom 按領域如何分佈,是 2026 年 5 月這一時點的一個切面。請不要看絕對數量,而看決策集中在哪個領域。決策集中之處,正是該專案思考得最激烈的地方。

| 類別 | atom 數 | 備註 |
|---|---|---|
| combat | 47 | 戰鬥系統決策 |
| narrative | 38 | 敘事 5 層 |
| ui | 31 | UI·HUD |
| balance | 28 | 數值平衡 |
| level | 22 | 關卡設計 |
| character | 19 | 角色·voice_profile |
| meta·governance | 18 | 流程與規則 |
| qa·integrity | 16 | 驗證 |
| content | 14 | 內容量產 |
| operations | 14 | 運營工作流 |
| external_reference | 12 | 外部資料 |
| economy | 11 | 經濟與資源 |
| 其他 | 34 | 分類進行中 |

戰鬥(combat)最厚重、敘事緊隨其後的分佈,直接顯露出這個專案是以戰鬥為核心的 MMORPG,同時又不願放棄敘事比重的性格。"其他 34"是尚未確定類別的新決策,這一欄若變得過大,就是該動分類體系的訊號。截至 2026 年 5 月,合計為 304 個。

## A.4 驗證與運營材料

即使有工具與知識,若沒有確認其是否正常運轉的裝置,質量就會一路下滑。本節把這類確認裝置分為兩種來展示:週期性產出的報告,以及為事後追溯決策而留下的決策卡。

### A.4.1 報告

| 報告 | 頻率 |
|---|---|
| 每日構建報告 | 每天 |
| Alpha 差距報告 | 每週(10.3) |
| 衝刺質量報告 | 每兩週 |
| 里程碑 QA 報告 | 每個里程碑 |
| 季度覆盤 | 每季度 |

頻率就是報告的性質。每天產出的是狀態檢查,每週、每兩週是趨勢檢查,里程碑與季度是方向檢查。AI 貢獻最大的地方,是像每日、每週這樣反覆產出的報告的初稿撰寫,其案例在 10.3 中展開。

### A.4.2 決策卡

| 季度 | 決策數 |
|---|---|
| 2025 年第 4 季度 | 132 |
| 2026 年第 1 季度 | 156 |
| 2026 年第 2 季度(進行中) | 89 |
| 累計 | 547 |

每個季度都有 100 件左右的決策以卡片形式留存,這一事實本身就體現了"把決策當作記錄而非記憶來對待"的運營原則。第 2 季度的 89 件是季度中途時點的累計,屬於進行中的數值,到季度末會達到上一季度的水平。這些卡片積累起來、晉升為 A.3 的 atom 的這一流程,正是本系統的學習軸。

## A.5 會議分佈(參考)

會議既是時間流失最嚴重的地方,也是最快能體會到 AI 工具效果的地方。下表是把各季度的會議按類別歸併後的平均分佈,用作估算 17.3 中會議記錄系統輸入規模的參考資料。數值每個季度都有起伏,因此以區間記錄。

| 類別 | 季度平均 |
|---|---|
| 每日(daily) | 65\~70 次 |
| 戰鬥(battle) | 35\~45 次 |
| 美術(art) | 25\~30 次 |
| 問題(issue) | 8\~15 次 |
| 評審(review) | 6\~10 次 |
| 其他(1:1·外部) | 40\~50 次 |

每日會議最頻繁,戰鬥相關會議緊隨其後。它與 A.3 的 atom 分佈形狀相同,這一點意味深長。決策集中的領域,會議也集中。會議越頻繁的環境,會議記錄自動整理的效用就越大,其具體運營在 17.3 中說明。

## A.6 讀者參考

至此為止的所有表格,都是筆者環境的一張照片。它不是讓你照搬的清單,而請當作用同一套框架整理自己環境的樣本。團隊規模、品類、平臺不同,工具、atom 分佈、會議比重都會不同。重要的不是專案是否一致,而是"基礎 → 工具 → 知識 → 驗證"這四層在你自己的環境中是否也不斷裂地連貫銜接。這四層當中若有空白的一欄,那一欄就是接下來要動手的地方。
