# 附錄 C. 許可權·設定參考

本附錄是把正文中引用的工具與系統的許可權·設定彙集到一處的參考表。正文說明的是"為什麼要這樣運營",而真要應用到自己的環境時,還需要知道"那麼具體該把什麼值填到哪裡"。本附錄填補的正是這塊空白。

比起設定值本身,選擇這個值的理由更重要。與其原樣複製表中的數字,不如先讀一讀每個條目下面的簡短說明,再按照自己的團隊規模和風險水平來調整。如果是一個人工作,就無需劃分許可權等級;如果沒有外包,把外包相關的條目整塊刪掉即可。

使用本附錄有兩種方式。第一次搭建環境時,從 C.1 開始按順序通讀,像檢查清單一樣確認有沒有遺漏的條目。運營過程中出了事故時,先翻到 C.7(事故應對),找到對應的事故行,再往上回溯到它上方的預防條目。

## C.1 LLM API 許可權

LLM API 金鑰與成本直接掛鉤,一旦洩露就會立即演變成金錢事故。因此先從金鑰管理和許可權等級講起。

### C.1.1 金鑰管理

| 金鑰 | 保管 |
|---|---|
| Anthropic API | 環境變數 + 1Password |
| OpenAI API | 環境變數 + 1Password |
| 自託管 | 公司內部 |

金鑰不寫進程式碼,而是通過環境變數注入,原件放在金鑰管理工具(如 1Password)裡。最常見的事故是把金鑰寫在程式碼裡連同 git 一起提交,因此在 git 中包含金鑰一律禁止。

### C.1.2 許可權等級

| 使用者 | 許可權 |
|---|---|
| 總監·資深 | full(負責運營 cost cap) |
| 普通成員 | 按任務設定 cap |
| 外包 | 按任務限一次 |

許可權不按信任劃分,而按責任的大小劃分。擁有 full 許可權的人同時承擔管理成本上限(cost cap)的責任。對外包只按任務單位開放一次,任務結束後即收回。

## C.2 工具設定標準

每種工具的推薦設定各不相同,但核心是把分析類工作和創意類工作分開。分析必須可復現,創意則需要多樣性。

### C.2.1 Claude Code

下面是 Claude Code 的基本設定示例。逐行來看:固定模型,開啟擴充套件思考,設定 token 上限,開啟自動更新,並掛上一個在提交提示詞時注入記憶的 hook。

```json
{
  "model": "claude-opus-4-8",
  "extended_thinking": true,
  "max_tokens": 100000,
  "auto_update": true,
  "hooks": {
    "UserPromptSubmit": ["~/.claude/hooks/inject_memory.py"]
  }
}
```

`model` 的值只是示例。模型名稱會隨每一代而變化(本示例以寫作時點為準),因此不要照抄,而要用 `/model` 確認當前可用的最新名稱再填入。即使名稱變了,本書的工作流骨架依然照常運作(參見附錄 K)。

掛在 `hooks.UserPromptSubmit` 上的指令碼,負責在每次提交提示詞時自動嵌入相關的記憶片段。這套記憶注入機制會在正文第 24 部分詳細展開。

**C.2.1.1 工具許可權模式(allow / deny)**

在同一個 `settings.json` 中,許可權用 `permissions` 塊單獨存放。可以讓 AI 不經人工批准就自動執行的工具寫進 `allow`,而一旦出一次事故就會致命、必須阻止自動執行的工具寫進 `deny`。寫法為 `工具(命令模式)` 形式,`:*` 表示"以該命令開頭的所有呼叫"。

```json
{
  "permissions": {
    "allow": [
      "Bash(ls:*)",
      "Bash(git status:*)",
      "Bash(git diff:*)",
      "Read(*)",
      "Grep(*)"
    ],
    "deny": [
      "Bash(rm -rf:*)",
      "Bash(git push --force:*)"
    ]
  }
}
```

像讀取·搜尋(`Read`·`Grep`)和狀態查詢(`git status`·`git diff`)這類不會造成不可逆後果的命令,用 `allow` 自動放行,以減少批准彈窗帶來的疲勞。反過來,像 `rm -rf`、`git push --force` 這類一次失誤就無法恢復的命令,無論把自動放行的範圍放得多寬,都要寫進 `deny`。

運營原則有四條。

| 原則 | 內容 |
|---|---|
| 從白名單起步 | 自動放行從最小集開始,僅在必要時才加入 `allow` |
| 危險命令顯式攔截 | `rm -rf`·`git push --force` 一律 `deny` |
| 定期清理 | 每季度複查 `allow`,刪掉不再使用的許可權 |
| 按領域分離 | 把全域性許可權和專案許可權分開,讓家用 PC 和公司 PC 擁有不同的策略 |

`allow` 列表並不是靜態配置,而是工作累積的痕跡。重複的工作越多,它就越長,因此最好一併配上按季度清理的週期。這套許可權運營的背景會在正文第 1 部分第 3 章詳細展開。

### C.2.2 自研工具

| 設定 | 推薦值 |
|---|---|
| LLM temperature(分析) | 0 |
| LLM temperature(創意) | 0.7 |
| Cache TTL | 1 小時 |
| Cost cap(每日) | 按工具定義 |
| Backup 週期 | 每日 |

分析類呼叫把 temperature 設為 0,讓相同輸入產生相同輸出。驗證·lint·分類這類結果不能有波動的工作都屬於此類。反過來,發散想法或生成初稿則給予 0.7 左右的多樣性。成本上限不設統一標準,而是按工具分別設定,因為每種工具的呼叫頻率和 token 消耗各不相同。

## C.3 git 許可權

| 分支 | 許可權 |
|---|---|
| main | 僅總監·資深可 push |
| feature/* | 所有成員 |
| protected branches | 強制程式碼評審 |

main 分支禁止直接 push,所有變更都要在 feature 分支經過程式碼評審後再合入。force-push 會覆蓋協作歷史,因此予以禁止,只有在不得已需要事故恢復時,才經總監與程式碼負責人(code lead)一致同意後開例外。

## C.4 檔案系統許可權

文件資料夾按 Layer 結構(L0\~L4)劃分許可權。越往上影響範圍越廣,寫許可權收得越窄;越往下工作越分散,寫許可權放得越寬。

| 資料夾 | 許可權 |
|---|---|
| docs/L0_vision/ | 總監 write,所有人 read |
| docs/L1_systems/ | 領域總監 write,所有人 read |
| docs/L2_content/ | 負責人 read·write |
| docs/L4_meta/ | 所有人 write |
| team_memory/各使用者/ | 僅本人 read·write |

願景(L0)只由總監書寫,所有人可讀。系統(L1)由領域總監書寫。內容(L2)由負責人書寫,元資訊·臨時(L4)則任何人都可書寫。個人記憶僅本人可訪問。這套 Layer 結構本身會在正文第 6 部分講解。

## C.5 備份·恢復

| 資料 | 備份 |
|---|---|
| git repo | git 本身 + 遠端備份 |
| 表格(Excel) | git + 每日備份 |
| 使用者資料 | DB 備份(伺服器標準) |
| 會議記錄·決策 | git |
| 記憶 | 每日自動同步 |

每種資料的備份路徑各不相同,但原則只有一個:越是丟失後難以恢復的資料,越要做雙重保管。文本資產(會議記錄·決策·程式碼)有 git 就等於有了備份,二進位制或伺服器資料則另設單獨備份。恢復時間目標(RTO)定在 4 小時以內,但這個值要按團隊能承受的停機時間來調整。

## C.6 安全

| 領域 | 規則 |
|---|---|
| 向外部 LLM 傳送敏感資料 | placeholder 或自託管 |
| 支付·個人資訊 | 絕不傳送給 LLM |
| 引用外部資料 | 註明出處 + 法務審查 |
| 使用者資料保護 | 匿名化 + 遵守 GDPR |

最容易遵守、卻最常被破壞的規則,就是"不把敏感資料傳送給外部 LLM"。因為工作緊急時,把真實資料直接貼上進去的誘惑很大。支付·個人資訊一律設為禁止傳送,若需要分析,就用 placeholder 替換,或使用自託管模型。

## C.7 事故應對

| 事故 | 應對 |
|---|---|
| 因 LLM 幻覺發出錯誤資訊 | 立即撤回 + 上報 |
| 成本超出 cap | 自動阻斷 + 複查 |
| 著作權事故 | 1 小時內停止使用 + 法務 |
| 安全事故(key 洩露) | 立即更換金鑰 + 審查使用記錄 |
| 資料丟失 | 備份恢復 + 事故分析 |

很多時候,比起阻止事故,儘快止損更為重要。表中的應對都遵循"先停下,再分析"的順序。key 洩露時,先別追究原因,而是先更換金鑰並檢視使用記錄。成本超過上限時,先自動阻斷再複查。這套應對流程要用文件明確固化下來,並定期演練,好讓真出事故時能毫不猶豫地運轉起來。
