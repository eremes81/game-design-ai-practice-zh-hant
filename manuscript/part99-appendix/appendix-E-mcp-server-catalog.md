# 附錄 E. MCP 伺服器目錄(遊戲策劃視角)

MCP(Model Context Protocol,模型上下文協議)是 LLM 以標準化方式連線外部工具與資料的通道。正文第 20 部分講過專案管理類 MCP,但可以引入遊戲策劃工作流的 MCP 伺服器遠不止於此。本附錄把這些候選項彙總起來,一目瞭然,並按引入順序標註了優先順序,是一份目錄。

本目錄的目的不是"把這些全都裝上",而是"需要時知道從哪裡挑選"。一次性接入多個 MCP,就分不清是哪個引發了問題。請按照 E.4 的引入週期,一個一個地增加。

使用方法如下。起初只看 E.2.1 的 P0 列表。基本功打牢後再進入 E.2.2(P1);當團隊出現特殊需求時,再考量 E.2.3(P2)或 E.3(自行開發)。擔心成本就先看 E.5,想為故障做準備就先看 E.6。

---

## E.1 MCP 的四大應用領域

MCP 伺服器按連線物件大致分為四類。遊戲策劃每天來回使用的工具,大多都落在這幾類之內。

| 領域 | MCP 伺服器 |
|---|---|
| 專案管理 | ClickUp、JIRA、Linear |
| 文件 | Confluence、Notion、Google Drive |
| 協作 | 團隊即時通訊工具(Slack、Discord 等) |
| 資料 | Excel、Google Sheets、DB |

專案管理對接任務與排期,文件對接策劃案與 wiki,協作對接團隊溝通,資料對接數值與道具表格。先弄清自己團隊已在使用的工具屬於哪個領域,引入的候選範圍自然就會收窄。

---

## E.2 推薦的 MCP 伺服器(遊戲策劃優先順序)

優先順序以"沒有它工作是否會卡住"為標準評定。P0 幾乎是所有工作的基礎,P1 有了會大為便利,P2 則視團隊情況而定。

### E.2.1 P0 —— 優先引入

| 伺服器 | 用途 | 備註 |
|---|---|---|
| Filesystem MCP | 訪問本地檔案 | 基礎 |
| Git MCP | 變更追蹤 | 必備 |
| 團隊即時通訊 MCP | 團隊溝通 | 推薦 |
| 協作工具 MCP(ClickUp、JIRA 等) | 任務 | 公司工具 |

Filesystem 與 Git 是 LLM 讀取資料、追溯變更歷史的基礎,因此最先接入。團隊即時通訊 MCP 引入團隊上下文,任務工具則直接把公司已在使用的那一款(無論是 ClickUp 還是 JIRA)連上。

### E.2.2 P1 —— 追加引入

| 伺服器 | 用途 |
|---|---|
| wiki MCP(Confluence、Notion 等) | wiki |
| Google Drive MCP | 外部共享資料 |
| Excel MCP | 直接查詢表格 |
| Mermaid MCP | 渲染圖表 |

P0 穩定後,再向文件與資料一側擴充套件。尤其 Excel MCP 能讓 LLM 直接查詢數值表格,在遊戲策劃中用途很廣。Mermaid MCP 能就地渲染設計圖示,不打斷文件化的流程。

### E.2.3 P2 —— 可選

| 伺服器 | 用途 |
|---|---|
| Discord MCP | 使用者社群 |
| GitHub MCP | 外部協作 |
| Linear MCP | 備選任務工具 |
| Notion MCP | 備選 wiki |

P2 要麼是備選,要麼專用於特定場景。運營使用者社群就接入 Discord,外部協作頻繁就接入 GitHub。Linear、Notion 是已引入工具的替代品,無需重複安裝。

## E.3 面向遊戲的專用 MCP(作者自行開發)

商用 MCP 填不滿的位置,就自己動手做。下面是作者針對遊戲策劃工作流自行開發的 MCP。它們都是為了從 LLM 直接查詢正文講過的那些系統(atom、決策卡、會議記錄)。

| 伺服器 | 用途 |
|---|---|
| Atom MCP | 檢索、查詢 atom |
| Decision Card MCP | 查詢、生成決策卡 |
| KPI Dashboard MCP | 儀表盤資料 |
| Meeting Notes MCP | 檢索會議記錄 |

這四個處理的是商用工具沒有的內部資產(知識 atom、決策歷史、會議記錄)。自行開發負擔較大,建議推遲到 E.4 週期的最後階段,等到確實清楚哪些是商用 MCP 無法填補的,再著手為好。

## E.4 MCP 引入週期

MCP 一次性全部接入,會讓問題根源難以辨認。下面的週期,是把"一次一個、穩定之後再下一個"這一原則沿時間軸展開的結果。

```mermaid
flowchart LR
    A["1周<br/>試點 1 個 Filesystem"] --> B["1個月<br/>追加 Git + 團隊即時通訊"]
    B --> C["3個月<br/>穩定執行 5~7 個"]
    C --> D["6個月<br/>評估自研 MCP"]
    classDef code fill:#dbeafe,stroke:#2563eb,color:#0b2545;
    classDef human fill:#fde68a,stroke:#b45309,color:#000;
    class A,B,C code;
    class D human;
```

核心規則只有一條:不要一次同時引入 5 個。每接入一個新的 MCP,都請先花幾天看它這一個是否穩定運轉,再進入下一個。

## E.5 MCP 運營成本

| 伺服器 | 成本 |
|---|---|
| 外部 MCP(開源) | 僅基礎設施 |
| 自行託管 | 基礎設施 + 運營 |
| 商用 MCP | 月度訂閱 |

成本結構分為三種。開源 MCP 只需承擔執行的基礎設施費用,自行託管在此之上再加運營人力成本,商用 MCP 則要付訂閱費。運營 8\~10 個時,月度成本大致估算在 $50\~200 一檔,但這會因配置不同而大幅變化,故只作方向參考。

## E.6 事故應對

| 事故 | 應對 |
|---|---|
| MCP 伺服器故障 | 核心伺服器採用 fallback 執行 |
| 許可權事故(誤改資料) | 優先 read-only |
| 資料洩露 | 敏感資料自行託管 |
| 成本暴漲 | cap + 監控 |

MCP 把外部工具直接連到 LLM,因此一次錯誤的寫入就可能毀掉真實資料。所以預設設為 read-only,寫入許可權只對確有必要的伺服器開放。核心伺服器要為故障預備 fallback,處理敏感資料的 MCP 則用自行託管而非外部來執行。成本方面用上限(cap)與監控一併遏制。

## E.7 引入前的自查清單

如果說前面幾節講的是"接入什麼、按什麼順序、花多少錢",那麼這張表彙總的是在真正接入某一個 MCP 之前,需要自己逐條通過的專案。不必從頭重讀整份目錄,每次新增 MCP 時,只需重新核對這五行即可。這五個專案,各自把前面某一節的核心規則壓縮成了一行。

| 檢查項 | 通過標準 | 依據小節 |
|---|---|---|
| 屬於哪個領域 | 明確屬於專案管理、文件、協作、資料中的哪一個 | E.1 |
| 是否是當下所需的優先順序 | 遵守 P0 穩定之後才 P1、再 P2 的順序 | E.2 |
| 是否逐個接入 | 不一次同時引入多個 | E.4 |
| 許可權是否最小 | 預設 read-only,寫入只給確有必要的伺服器 | E.6 |
| 是否有成本上限 | 同時掛上上限(cap)與監控 | E.5 |

五個專案中最常被跳過的一欄,是"是否逐個接入"。因為一次上多個 MCP,一旦出問題就分不清是哪個伺服器的錯。只有五行全部通過時才接入那個 MCP;哪怕只卡住一行,也把該伺服器推遲到下一個週期。
