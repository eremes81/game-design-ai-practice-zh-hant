# 1.1 遊戲策劃與 Claude Code 的第一次相遇

黑色的畫面亮了起來。游標在閃爍。一位有著 24 年資歷的遊戲策劃坐在它面前。用 PPT 和 Excel、Wiki 和 Figma 工作了 24 年的手,在鍵盤上停頓了片刻。那有點像從前還有電腦培訓班的年代裡的 DOS。在那之後,終端這個東西只在程式設計師的桌面上才見得到。不知道該敲什麼,而且彷彿一敲錯就會弄壞什麼。這一份猶疑,正是本書的出發點。

大多數人會在這裡關掉視窗。然後在會議上一遍遍重複"我們也得做點什麼才行"。本章要做的,是不關掉那扇視窗,陪你一起坐在熬過頭 30 分鐘的那個位置上。目標不是什麼宏大的匯入戰略,而是把"在閃爍的游標面前敲點什麼、距離感就會消解"這件事,實打實地放到你手裡。

---

遊戲策劃第一次坐到 Claude Code 這類 AI 程式設計工具面前時,新奇與不適會在同一個位置同時湧起。這兩種情緒相互衝突這件事本身,就是匯入的第一條線索。

新奇的理由很明確。原本要花上半天的資料表一致性檢查,幾分鐘就完成了;拖沓冗長的會議記錄被彙總成決策事項的表格;一年前被埋沒的策劃案,用一句自然語言就能重新調取出來。

不適的理由也同樣明確。黑色的畫面、閃爍的游標、英文命令,跟日常的工作景象太不一樣了。遊戲策劃的一天是在 GUI 之上流動的,而往黑色終端裡敲字這件事,跟職業身份很難貼合。不過這份不適並不是工具的缺陷,而是習慣了 GUI 的人所需付出的適應成本。光是承認這一點,距離感就已經消解了一半。

本書就是一本想要縮短這份距離感的書。1.1 陪你一起坐在第一次相遇的位置上,梳理該看什麼、該嘗試什麼、又有什麼可以先放一放。

---

## 1.1.1 為什麼是現在,遊戲策劃必須用 AI

遊戲策劃比其他職能更晚才匯入 AI 的浪潮。處理程式碼的人先進去,設計師、美術接著進去。策劃則常常陷入一遍遍重複"我們也得做點什麼才行"、卻一拖再拖的模式。

拖延的理由是合理的。策劃的產出不像程式碼那樣定型化,而是文本、表格、圖示、會議、口頭共識混雜在一起。AI 輸出的可信度看起來偏低,煞有介事的謊言又很危險,而且 AI 是否真的理解遊戲系統也令人懷疑。

然而在 2024\~2026 年之間,有三件事發生了變化。

第一,AI 模型的推理能力越過了臨界點。它不再停留在簡單的句子生成,而是能處理複雜的系統設計、一致性驗證、影響分析。最新的 Claude 系列能輔助遊戲策劃工作流的相當一部分。不過這並不意味著可以把全部都交給它。驗證與責任仍然在人這一邊。(輔助的幅度因工作型別和團隊成熟度而大相徑庭——作者推測,未經驗證。)

第二,驅動框架(harness)成熟了。Claude Code 這類工具不是單純的聊天。它會直接讀寫檔案、執行命令,再把結果作為輸入接回來。這跟人工作的方式很像。

第三,記憶、atom、skill 這類運營技法已經落地。AI 不再是用一次就完事,而是有了一套方法論:把團隊的知識累積起來,讓它隨著時間推移越來越聰明。本書後半部分要講的核心,正是這種累積。

這三件事一旦匯合,對遊戲策劃來說,匯入 AI 也就成了一個合理的時間點。趁還沒更晚之前開始,是划算的。

## 1.1.2 Claude Code 是什麼——與其他工具的區別

策劃常接觸的 AI 工具有兩類。一類是往聊天框裡拋問題的聊天機器人型(ChatGPT、Claude 網頁應用),另一類是在程式碼編輯器裡做自動補全的編輯器結合型(Cursor、Copilot)。

遊戲策劃的工作不是程式碼,而是文件、表格、關係。Claude Code 的強項在於:它能看到、理解並操作人工作的整個資料夾。不必像聊天機器人那樣每次都把資料複製貼上進去。

用辦公室來打比方,聊天機器人型是前臺諮詢臺。問一次答一次,資料每次都得重新拿出來。Claude Code 則更接近鄰座的同事。它知道資料在哪裡,會用自己的手開啟檔案,把結果整理好再放回桌上。同樣是 Claude,讓它坐到哪張桌子上,擅長的事情就會隨之不同。

安裝和配置在 1.0 裡講。1.1 專注於在頭 30 分鐘裡體驗什麼能減少距離感。頭 30 分鐘分為四個區段,每個區段都會讓一部分距離感分階段地消失。

### 頭 5 分鐘——檢視

開啟終端、執行 Claude Code,黑色畫面亮起,游標閃爍。很多人會停在這個位置,但一停下,就錯過了消解距離感的第一個機會。輸入一句自然語言。

```
幫我概括一下這個資料夾裡有什麼
```

既不是程式碼也不是命令,就是一句話。Claude Code 會掃描資料夾結構,整理出有哪些檔案、看起來是處理什麼的專案,然後作答。在裝著策劃文件的資料夾裡敲下這一句,大致會得到這樣的回應。

```text
> 幫我概括一下這個資料夾裡有什麼

我掃描了這個資料夾。看起來是遊戲資料·策劃文件的工作資料夾。

  檔案型別        數量    內容推測
  ─────────────   ────    ───────────────────────────
  .xlsm            12     資料表(道具·任務·NPC 等)
  .md              34     策劃案·會議記錄草稿
  .png             88     UI 原型·參考圖
  子資料夾          6     /data /docs /ref /meeting /export /tmp

觀察:
  - /meeting 資料夾裡堆積了最近一週的 5 份會議記錄。
  - item_table.xlsm 與 quest_table.xlsm 似乎共享同一個 ID 列
    (FK 候選)。
  - /tmp 資料夾裡有多個臨時 export 檔案——可能是待清理物件。

要先看哪一個?
```

從這一次回應裡,"這個工具聽得懂的不是命令,而是自然語言"這一事實會切身地進入你的身體。不用親自開啟資料夾,就能拿到一張梳理好的圖——什麼在哪裡——這種體驗,會當場削掉一半的距離感。

### 接下來 5 分鐘——搜尋

讓它做一點小搜尋。比如"告訴我最近一週內修改過的 5 個 Markdown 檔案",或者"含有'獎勵'這個詞的檔案在哪裡?"這類請求。策劃每天都要開啟"在檔案中查詢"、敲入關鍵詞、滾動結果的活兒,Claude Code 用自然語言接過來,整理好再還給你。這個工具替你幹掉每天的雜活——這種感覺會在第二個 5 分鐘裡站穩腳跟。

### 接下來 10 分鐘——轉換

讓它做一點小轉換。比如"從這份會議記錄裡只提取決策事項,做成表格",或者"把這張 Excel 表的第 1\~10 行轉成 Markdown 表格"這類請求。原本用手要花 5\~10 分鐘的轉換,在很短的時間裡就被處理掉——這種體驗會帶來一種感覺:工具不止於替你搜索,更是在幫你騰出時間。

### 最後 10 分鐘——驗證

止步於此之所以危險,是因為 AI 會說煞有介事的謊話。讓它自己去質疑剛剛做出來的輸出。

```
幫我再確認一下剛才做的表格和原文是否一致。有沒有漏掉的條目?
```

於是 Claude Code 會重新讀一遍原文,把它跟自己的輸出逐行對照,報告出不一致之處。實際上在這個區段裡,經常會出現這樣的畫面。

```text
> 幫我再確認一下剛才做的表格和原文是否一致。有沒有漏掉的條目?

我把原文(meeting_0603.md)和剛才做的表格重新對照了一遍。
找到了 3 處不一致。

  ⚠ 遺漏   "教程獎勵下調 50%" —— 在原文第 12 行,但表格裡漏掉了
  ⚠ 筆誤   負責人 "金某某" → 表格裡誤寫成了 "李某某"
  ⚠ 模糊   "獎勵再議" —— 是決策還是擱置,原文表述不清。
           我擅自把它歸入了'決策',但需要確認。

要我重新做一張修正後的表格嗎?模糊的那條要怎麼處理,
告訴我後我會照著改。
```

工具懂得質疑自己的輸出,並且這份質疑是和人一起來做的——這是最後 10 分鐘的核心。像第三條那樣,反過來問"我是擅自判斷的,請你確認一下"的這種態度,正是把驗證留在人手裡的安全閥。

30 分鐘過去,距離感的 80% 已經消失了。剩下的 20% 會在接下來的各章裡慢慢減少。

## 1.1.4 在公司裡看到的景象——中等規模團隊的 6 個月

作者作為設計總監運營的某個 MMORPG 專案(以下稱"專案A"),已與策劃團隊(4\~5 人)用以 Claude Code 為中心的工作流運營了約 6 個月(專案A 的整個開發團隊為中等規模,10\~50 人)。這裡轉述幾個景象。

只把最抓得住手的一件拿出來,按實測來算。這是橫跨 30 多張資料表的 FK(外部索引鍵)一致性檢查。它是用人眼去追蹤"一張表的 ID 在另一張表裡是否被正確引用"的工作,表越多,組合就以幾何級數膨脹。

- **Before**:一位策劃輪流開啟各表對照 ID。30 多張表巡視一遍要半天(約 4 小時)。中途注意力一斷,就會有漏掉的行。
- **After**:關係檢測工具自動對照表間 FK,只把斷裂的引用列成清單輸出。巡視一遍約 5 分鐘。

從半天到 5 分鐘。這一條我不會去做一般化。其他工作的節省幅度更小,或者會新添出審閱時間。同樣這 6 個月裡看到的其他景象,只用方向和比例來記。

- 會議記錄決策提取(每週累積 5\~10 件):原本人要靠搜尋、滾動去追蹤 → 自動提取成表格。追蹤的負擔幾乎消失。
- GDD(Game Design Document,遊戲設計文件)初稿:撰寫時間減到一半以下,代之以審閱、打磨的時間增加了。總量是減少了,但工作的重心從'寫'移到了'判斷'。
- 資料表關係圖:原本在會議上要反覆口頭說明的依賴結構 → 用互動式 HTML 一次性生成出來共享。

每個工具一旦做成,6 個月裡累積下來節省的時間,按作者的體感不是以人-周(person-week)計,而是以人-月(person-month)計(精確的合計未測量,為估算值)。靠那些時間,得以專注於更深的策劃。

這類工具一旦做成,就能長久地幹活。不過'長久'並不等於'無人'。要運營它的人和驗證結構一起配齊,才能長久;只留下工具而人走了,兩個季度內就會腐壞。本書後面的各部分,會講上述每個工具是如何被做出來、又如何運營的。

## 1.1.5 恐懼與期待——坦誠地面對

來坦誠地點一點遊戲策劃在 AI 工具面前常有的恐懼。不迴避而是去面對,是匯入的第一步。

"AI 會取代我的工作"這份恐懼,對了一半,也錯了一半。單純的雜活(一致性檢查、文件轉換、搜尋)會被 AI 取代,但決策、優先順序、玩家情緒的設計,它取代不了。反倒是善用 AI 的策劃,從雜活中解放出來,專注於本質。不妨自問:"我的工作裡,雜活和本質的比例是多少?"如果雜活佔 70%,那本質的 30% 原封不動還是你自己的,而那 30% 變得更重要,才是關鍵。

"AI 錯了,責任誰來擔"這個問題也經常出現。對策劃的決策所負的責任,永遠是策劃自己的。不經驗證就照搬 AI 的輸出,那是策劃的失誤,而不是 AI 的失誤。把驗證流程一併設計進去,是匯入的一部分。1.1.3 最後 10 分鐘裡看到的'讓它質疑自己的輸出',就是這套流程裡最小的那粒種子。

"不太懂程式碼所以用不了"這份恐懼很快就會解開。Claude Code 用自然語言執行,不懂程式碼就以不懂的樣子起步即可。因為會和 AI 一起讀它寫出來的指令碼,幾個月下來,簡單的指令碼就能讀懂並修改了。學習會自動地跟上來。

"工具變得太快"也是常見的擔憂。要把模型、功能、趨勢全都追上,人會累垮。只把對自己工作流有幫助的 1\~2 個功能深入學透,其餘的等需要時再看。

先打個預防針。即便 1.1.3 的回應畫面看起來很光滑,實際的頭 30 分鐘裡,會混著答偏的回答、張冠李戴的檔案概括、卡頓的輸出。那是正常的。本書講的不是光滑的成功故事,而是更多地講:當輸出答偏了,要怎麼重新請求把它糾正過來。

## 1.1.6 本書的使用方法

本書由 24 個部分構成。不必從頭到尾按順序讀。從下面三種模式裡挑一個適合你處境的就行。

| 模式 | 路徑 | 耗時 |
|---|---|---|
| 匯入模式 | Part 1(匯入) → Part 2(資訊架構) → 你自己的領域 1 個 | 1\~2 個月 |
| 全量模式 | Part 1\~2 → 各領域(3\~15) → 流程(16\~19) → 運營(20\~24) | 6 個月\~1 年,適合以團隊為單位 |
| 問題解決模式 | 附錄索引 → 反向回到對應章 | 約 1 周,手頭有問題時 |

如果拿不準選哪條路,按你更接近哪一邊來分就行。**如果你是遊戲之外的策劃、PM 或普通職場人**,可以不選上面三種模式,而走「通用職能之路」(第 1·2 部 → 第 17 部會議記錄 → 第 16 部協作 → 第 18 部決策 → 第 21·22 部自我改進·治理)——即便跳過遊戲領域的章節,核心骨架照樣立得起來,而每一章的「遊戲之外的應用」方框,就是把內容搬到你自己職能上去讀的那座橋(索引見附錄 F.5)。如果沒時間,只跟著 17.1 → 16.2 → 22.1 → 21.1 這四章走也可以。**如果你是剛開始接觸 AI 工具的非專業讀者**,就用'匯入模式',只抓住你自己的領域(或最接近的領域)一個、一路讀到底,而深度領域的部(4·8·11 等)只取匯入部分'給非專業者的一行話',需要時再下沉到正文。

本書的所有章節都不走到學術深度,而是停在可運營的層面。把中等規模團隊裡實際跑了 6 個月的技法原樣搬過來,陪你一起走那條從小處起步、再做大的路,就是目標。

## 動手試試

**setup**
1. 開啟終端(Windows 用 PowerShell,macOS 用終端)。
2. 移動到彙集了策劃文件的資料夾,然後執行 Claude Code(安裝見 1.0)。
3. 把計時器設成 30 分鐘——5 分鐘(檢視)·5 分鐘(搜尋)·10 分鐘(轉換)·10 分鐘(驗證)。

**prompt**(每個區段敲一行,按順序敲下去)
```
① 幫我概括一下這個資料夾裡有什麼
② 含有'獎勵'這個詞的檔案在哪裡?
③ 從這份會議記錄裡只挑出決策事項做成表格
④ 幫我再確認一下剛才做的表格和原文是否一致。有沒有漏掉的條目?
```

**verify**
- 在 ① 中,用眼睛對照一下資料夾結構的概括是否和實際資料夾相符。
- ④ 的不一致報告只要出來哪怕一條就算成功。這意味著你親眼看到了 AI 質疑自己輸出的那一幕。
- 就算出來答偏的回答也不算失敗。像"剛才那個答錯了,只重看這個檔案"這樣重新請求,直到這一步,才是頭 30 分鐘的練習。

### 單人精簡版

如果既沒有團隊也沒有公司資料夾,作為個人,就在你自己 PC 上隨便一個工作資料夾(例如下載資料夾、筆記資料夾)裡,只敲上面的 prompt ① 和 ④。用 ① 確認"它聽得懂自然語言",用 ④ 確認"可以質疑它的輸出",那麼本章的兩個核心,一個人在 5 分鐘內也能切身體會到。
